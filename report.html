1Executive summary

Pi Durable is an experimental durable agent harness from Earendil (makers of the Pi coding agent). It is a framework for building agentic applications — coding agents included — that run anywhere there is a JavaScript runtime, support infinitely long conversations, survive crashes and redeploys, and let multiple humans steer the same agents.

Everything the harness does — model calls, tool calls, compaction, and your own application state machines — is a durable task that checkpoints before advancing. All changes flow through atomic commits to a storage backend (memory, SQLite, JSONL, or your own). If the process dies, a new process opens the same storage and continues from the last checkpoint.

Kubernetes fit

One Pod = one harness over one storage (built-in backends are single-owner). SQLite on a PVC survives restarts; harness.resume() picks up interrupted work. Scale out by running multiple agents, or implement a Postgres backend for true HA.

Giving it tasks

Wrap root.submit({content, requestId}) in an HTTP endpoint. The requestId makes submissions exactly-once — CI jobs, webhooks and bots can retry safely. Stream progress with watchEvents() over SSE/WebSocket.

Main caveats

Experimental API (pin versions). No built-in multi-process locking/HA. Hard power loss can lose the last un-fsynced SQLite commit. Built-in tools get real filesystem/shell access — isolate per conversation.

2What Pi Durable is

Pi the coding agent runs on your machine, inside a terminal, driven by one person — if it dies, you look at what happened and tell it to continue. Pi Durable exists because Earendil wants agents that run anywhere, can be reached from different surfaces, support infinitely long conversations, survive catastrophic failures, and let multiple humans steer the same agent.

  • Not a replacement for the pi coding agent. It's a framework; the coding agent is one possible application built on it. They share code (pi-ai) and principles: minimalism and malleability.
  • ~15,000 lines of source (~150k tokens with GPT, ~250k with Claude) — deliberately small enough for an agent to read and build on. Storage backends alone are ~3,000 lines you can usually skip.
  • Built on @earendil-works/pi-ai (model access) and @earendil-works/chord (document state / contexts).

3Core concepts

ConceptMeaning
HarnessOne open storage plus the machinery that runs agents on it. All changes go through one line of atomic commits; nothing is shown before its commit is stored.
ConversationA transcript — an immutable, ordered list of entries. root() creates the root conversation on first use (same one after every restart). You can create more conversations and fork them at any point.
EntryOne immutable transcript record: user message, model response, tool result, system prompt change, reset — or your own kinds. The model sees entries from the newest reset onward.
CommitAn atomic write. A commit can append entries, edit documents, and create tasks together — all or nothing.
DocumentTyped JSON state stored next to the transcript and changed in commits. Built-ins hold agent config (pi.agent), live run state (pi.live), queued messages (pi.inbox), spend (pi.usage).
TaskA durable state machine that saves a checkpoint at every step, so a restarted process continues from the last one. Every task has an owner (a conversation or another task). Built-ins: pi.generation (model call), pi.tool, compaction.
SubmissionSomething you hand to a conversation — user input or an entry to write — which you can wait for. Carries an optional requestId for exactly-once semantics.
Turn / RunA turn = one model response and its tool calls. A run = the turns from an input to its final answer. A conversation is busy while a run is going.
ExtensionA named bundle of tools, system prompt sections, hooks, wrappers, and tasks. Installed in a registry; conversations select extensions by name.
RegistryThe extensions this process installed. It can change while the harness runs — new work uses the new state.
AgentWhat a conversation runs with: model, thinking level, selected extensions/tools, instructions, working directory. Stored per conversation as names in pi.agent.

One answered input, as entries and tasks

submit(input) → pi.user
  pi.generation → pi.system (only if the prompt or tools changed), pi.assistant (tool calls)
    pi.tool × n → pi.tool-result × n   (owned by the generation, which waits for them)
  pi.generation → pi.assistant (answer) → submission done

Ownership tree

Tasks and conversations form one ownership tree. Aborting a task aborts what it owns, bottom-up — every task cleans up its own effects first. A subagent is the same pattern: a conversation owned by the tool call that started it.

4Features in depth

4.1 Durability — survives crashes

  • Every step of a run is a task that stores a checkpoint before it moves on. If the process dies (laptop sleep, container redeploy, OOM), a new process opens the same storage, finds the unfinished tasks, and continues each from its last checkpoint: harness.resume().
  • A model request cut off mid-stream is sent again; the partial answer stays in the transcript, marked as aborted.
  • A tool call cut off mid-run reruns only if it declared replay: "safe"; otherwise the model is told the call was interrupted, with the output stored so far, and decides what to do.
  • Exactly-once submissions: a requestId makes a submission idempotent — a client that retries after a crash gets the original submission back instead of asking twice. harness.submission(id) re-acquires a submission by ID after a restart.
  • Queued messages stay queued across restarts. Subagents continue from where they left off; a replay-safe subagent tool finds its subagent again and waits for its answer.

4.2 Long runs, anywhere

  • Storage backends: memory, SQLite (Node), JSONL — plus a conformance suite and benchmarks for your own backend. The SQLite/JSONL code uses no Node APIs, so with a small adapter it runs on Bun or inside a Cloudflare Durable Object.
  • Custom backends are cheap: the storage interface is small; easy to implement over Postgres or a key-value store.
  • Single-owner rule: one process owns a storage at a time; other clients attach to that process. No cross-process locking in built-in backends (a key design constraint for k8s — see §6).
  • Bounded memory: the harness keeps only the working set in memory — active transcripts (naturally bounded by the model's context window via compaction), live tasks, pending submissions. Everything else stays on disk until needed.
  • Execution environments are pluggable too: a Node env gives tools local files/shell; a custom env can expose remote execution, so the harness runs on one machine while its tools run on another. The env function builds the environment per tool call from the conversation's working directory.

4.3 Infinitely long conversations

  • Compaction is a durable background task: when context nears the model limit, older messages are summarized in the background and placed at the next turn boundary. The conversation only waits for a summary if the next request wouldn't fit otherwise; if the provider still rejects as too long, the harness compacts and retries once.
  • Older messages always stay in storage — searchable even after compaction or handoff.
  • Reset / handoff: starts a new context, optionally from a handoff note. A tool can request it by returning control: { handoff }. Nothing is deleted, so later tools can still search everything before the handoff.
  • Tunable via settings: reserveTokens (wait-for-summary threshold) and backgroundTokens (start background summary this far early).

4.4 Many conversations at once

  • One harness runs as many conversations as you need, concurrently — none blocks another.
  • Forks: a conversation can fork another at any point in its transcript and sees the parent's history up to that point without copying it. Think Slack channel = conversation, thread = fork of the message it replies to.
  • Per-conversation agent config: model, thinking level, selected extensions/tools, extra instructions, working directory. A reviewer next to the main agent can use a cheaper model, read-only tools, and its own checkout.
  • Forks start with the agent their parent had at the fork entry; task-owned conversations (subagents) start as copies of their owner's agent.

4.5 Extensions — pluggable everything, malleable while running

  • An extension is a named bundle of sections, tools, hooks, wraps (decorators), and tasks. The application installs extensions in a registry; each conversation selects which it uses and stores only their names.
  • System prompt is rebuilt from sections before every request; only what changed is re-sent (provider prompt caches stay warm); changes are recorded positionally in the transcript so restarts and forks see exactly what the model saw.
  • Malleable: installing an extension under an already-installed name replaces it in one step. A tool call already running finishes on the code it started with; the next call uses the new code. After a restart, conversations pick up whatever the new process installs.
  • A later extension's tool with the same name replaces the earlier one (e.g., a bash that runs inside a Python venv); wrapTool() decorates whichever tool won (e.g., timing every bash call).

4.6 Tools

  • Built-in CodingTools: read, write, edit, bash. Files and processes are only touched through the call's execution environment. Image support via an optional Photon WASM processor (worker-threaded on Node).
  • Custom tools via defineTool() with TypeBox schemas; args validated before execute(). Three result channels: output (for the model), structuredOutput (for programs calling the tool, schema-validated), details (for UIs).
  • api.output() streams running output to every client watching.
  • Replay policy: each call runs as its own durable task; intent is committed before it runs. After a crash, rerun only if replay: "safe"; otherwise the model gets an interrupted error result with partial output.
  • Calling tools from tools: api.executeTool() — nested calls are their own tool tasks with their own replay policy, owned by the caller. Keys make retry-after-crash idempotent (finished calls are returned, not restarted).
  • Access control: callers: ["model" | "tools"] restricts who may call a tool; modelTools narrows what the model is offered without taking tools away from other tools. deferred: true + a tool-search extension handles large tool sets (e.g., an MCP server's).
  • Code Mode: a codemode tool where the model writes JavaScript that calls the conversation's tools in a QuickJS sandbox. Scripts survive restarts: deterministic replay (virtual clock, seeded randomness) plus journaled results — finished calls are not run again.

4.7 Hooks

  • Hooks step into tasks — built-in ones (model response, tool call, compaction) and your own: rewrite a request before it goes to the model, block or rewrite a tool call, replace a result, keep a run going, write a summary yourself.
  • Several extensions can hook the same point; hooks run as a chain in selection order. A throw is reported and the chain continues (except beforeTool, where a throw blocks).
  • Memos: a hook that makes a decision stores it with the task — after a crash, the memo is found instead of re-deciding. This is how you build "ask Slack for approval exactly once" gates.

4.8 Custom durable tasks

  • defineTask() defines named state machines with phases, checkpoints, timers that survive restarts, and waiting on other tasks (on: [taskIds], policy failFast).
  • Tasks get the same machinery as built-ins. Ownership ties them to conversations or parent tasks; aborting propagates bottom-up with per-task abort handlers that clean up effects (e.g., refund payments when a sibling card is declined).
  • Foreground vs background: foreground tasks are part of the current work (an Esc aborts them); background tasks belong to the conversation but not its current turn — they outlive it (a subagent that should outlive the turn, a reminder that fires tomorrow).

4.9 Documents — durable application state

  • Typed JSON stored next to the transcript and changed in the same atomic commits — app state (todo lists, plans, tickets, sandbox assignments) can never disagree with the transcript that produced it.
  • Each document declares fork semantics: parent's value at the fork point (asOf), current value, or fresh.
  • UIs subscribe to committed values; sections can render documents into the system prompt (the model sees live state before every request).

4.10 Multiplayer & remote clients

  • Everything a UI needs is committed state → any number of clients can attach to any conversation: watch, join late, reconnect from the current view, steer.
  • viewState() + subscribe(): full current view first (transcript, streaming answer, running tools and output, queued messages, agent, usage), then only deltas.
  • watch() delivers the exact operations of every commit — small enough to send over a socket. watchEvents() maps commits into the pi coding agent's familiar events (more bytes on the wire).
  • Steering: submit({ content, whenBusy: "steer" }) reaches the model at its next model call; a plain submit queues behind the current work.

4.11 Subagents & usage

  • No built-in subagents, but they're a few lines: a tool creates an owned conversation (own model/instructions/tools), submits work, waits for the answer. The subagent is a durable conversation — survives crashes, counts its own cost, and a UI can show it under the call.
  • Per-conversation usage/cost tracking; tools can report usage; spend lives in the pi.usage document.

5Code examples

5.1 Minimal harness (SQLite, coding tools)

import { BACKGROUND_CONTEXT } from "@earendil-works/chord/context";
import { createModels } from "@earendil-works/pi-ai/models";
import { openaiProvider } from "@earendil-works/pi-ai/providers/openai";
import { createRegistry, Harness, CodingTools } from "@earendil-works/pi-durable";
import { NodeExecutionEnv } from "@earendil-works/pi-durable/env/node";
import { openNodeSqliteStorage } from "@earendil-works/pi-durable/storage/sqlite/node";

const context = BACKGROUND_CONTEXT; // every call takes a context for cancellation
const models = createModels();
models.setProvider(openaiProvider()); // reads OPENAI_API_KEY

const registry = createRegistry();
registry.install(CodingTools); // read, write, edit, bash

const harness = await Harness.open(
  await openNodeSqliteStorage("/data/agent.sqlite"),
  { models, registry, env: ({ cwd }) =>> new NodeExecutionEnv({ cwd: cwd ?? "/work") } },
  context,
);
harness.resume(); // continue any run a previous process left unfinished

const root = await harness.root(context, {
  agent: { model: { provider: "openai", modelId: "gpt-6.1-sol" }, cwd: "/work/repo" },
});

const job = { type: "input", content: "Fix the flaky login test", requestId: "job-42" } as const;
await root.submit(job, context);
// the process dies here, in the middle of a tool call…

// …a new process opens the same storage:
const harness2 = await Harness.open(await openNodeSqliteStorage("/data/agent.sqlite"), { models, registry }, context);
harness2.resume();
const root2 = await harness2.root(context);
// same submission, answered — no duplicate run:
const settled = await (await root2.submit(job, context)).wait(context);

5.2 Channels and threads (forks)

const channel = await harness.root(context);
const question = await channel.submit(
  { type: "input", content: "@agent why did the deploy fail?" }, context);
const answered = await question.wait(context);

// A thread forks at the message it replies to. Ownerless: no one's abort reaches it.
const thread = await channel.fork(answered.answer!, { ownership: { kind: "ownerless" } }, context);

// Both conversations work at the same time, neither blocks the other.
const inThread  = await thread.submit({ type: "input", content: "@agent can we roll it back?" }, context);
const inChannel = await channel.submit({ type: "input", content: "@agent who is on call today?" }, context);
await Promise.all([inThread.wait(context), inChannel.wait(context)]);

// The thread may search, but not deploy:
await thread.configure({ tools: { remove: ["deploy"] } }, context);

5.3 Custom tool with replay policy + streaming output

import { Type } from "@earendil-works/pi-ai";
import { defineTool, defineExtension } from "@earendil-works/pi-durable";

const searchIssues = defineTool({
  name: "search_issues",
  description: "Search the issue tracker",
  parameters: Type.Object({ query: Type.String() }),
  replay: "safe", // only reads — a rerun after a crash is fine
  execute: async (args, api) => {
    api.output(`searching for ${args.query}\n`); // streamed to every watcher
    return { content: [{ type: "text", text: await tracker.search(args.query) }] };
  },
});

const deploy = defineTool({
  name: "deploy",
  description: "Deploy a version to production",
  parameters: Type.Object({ version: Type.String() }),
  // no replay: an interrupted deploy is reported to the model, never repeated
  execute: async (args) => ({ content: [{ type: "text", text: await ci.deploy(args.version) }] }),
});

registry.install(defineExtension({ name: "ops", tools: [searchIssues, deploy] }));

5.4 Hook with a memo — approve once, survive restarts

import { defineExtension, hook, ToolTask } from "@earendil-works/pi-durable";

const Approval = defineExtension({
  name: "approval",
  hooks: [
    hook(ToolTask, {
      beforeTool: async (call, api, context) => {
        if (call.name !== "deploy") return undefined;
        // After a restart, the hook finds the stored answer instead of asking again.
        let approved = await api.memo("approval:deploy", context);
        approved ??= await api.memo("approval:deploy", await askInSlack(call), context);
        return approved ? undefined : { block: "Nobody approved the deploy." };
      },
    }),
  ],
});

5.5 Custom durable task with cleanup (payments)

const Payment = defineTask({
  name: "shop.payment", version: 1,
  initial: () => ({ phase: "charge" }),
  phases: {
    charge: async (task, runtime, context) => {
      // idempotency key: a crash rerun charges the card only once
      const charge = await bank.charge(task.input.card, `payment-${task.id}`);
      await runtime.commit(() => ({
        status: "terminal",
        outcome: charge.ok
          ? { status: "completed", result: charge.receipt }
          : { status: "failed", error: { message: charge.error } },
      }), context);
    },
  },
  // another payment failed, or the checkout was cancelled → refund
  abort: async (task, runtime, context) => {
    await bank.refund(`payment-${task.id}`);
    await runtime.commit(() => ({ status: "terminal", outcome: { status: "aborted" } }), context);
  },
});

// The parent waits for all payments; the first failure aborts the rest:
return { status: "waiting", checkpoint: { phase: "decide", payments }, on: payments, policy: "failFast" };

5.6 Durable application state (documents)

const Todos = defineDoc({
  kind: "app.todos", version: 1, scope: "conversation",
  history: "rewindable", fork: "asOf", // a fork starts with the parent's todos at the fork point
  initial: () => ({ items: [] }),
});

const Todo = defineExtension({
  name: "todo",
  tools: [
    defineTool({
      name: "todo", description: "Add an item to your todo list",
      parameters: Type.Object({ item: Type.String() }),
      execute: async (args, api, context) => {
        await api.commit(async (tx) => {
          const todos = await tx.doc(Todos, api.conversationId);
          todos.items.push(args.item);
        }, context);
        return { content: [{ type: "text", text: `Added ${args.item}` }] };
      },
    }),
  ],
  // the model sees the list before every request
  sections: [
    section("todos", async (input, context) => {
      const todos = await input.read.snapshot(Todos, input.conversationId, context);
      return todos?.items.join("\n") || undefined;
    }),
  ],
});

// a UI subscribes to the committed value
const todos = await harness.documentState(Todos, channel.id, context);
todos?.subscribe((value) => renderTodos(value?.items ?? []));

// A second client joins the thread while the agent is working.

render(view.value);

6Kubernetes deployment

The key constraint: one process owns a storage at a time (built-in backends have no cross-process locking). The natural k8s unit is therefore one Pod = one harness over one storage. Scale out by running multiple Pods (each its own agent/storage), not by scaling replicas of the same storage.

6.1 Architecture

One Pod owns one harness over one SQLite file on a PVC. External callers submit tasks over HTTP; progress streams back over SSE/WebSocket.

6.2 Step by step

  1. Image. Node base with the app (harness + API server):
# Dockerfile
FROM node:24-bookworm-slim
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
EXPOSE 8787
CMD ["node", "dist/server.js"]
  1. Server code. Wrap the harness in a small HTTP server:
    • On startup: Harness.open(sqlite at /data/agent.sqlite, …) → harness.resume() → serve. Mark ready only after resume completes.
    • POST /tasks with { conversationId?, content, requestId } → root.submit(…); return submission id + status.
    • GET /stream?conversationId=…&cursor=… → SSE from watchEvents(); cursor = last event id → lossless reconnect.
    • POST /steer → submit({ whenBusy: "steer" }).
    • Auth middleware on all routes (whoever can use the route runs the agent on your API credits).
  2. Manifest.

  1. Failure behavior.
FailureWhat happens
Pod crash / restartk8s restarts the Pod on the same PVC → harness.resume() continues interrupted runs from checkpoints. Known requestIds are retrievable via harness.submission(id).
Node loss / rescheduleSame, as long as the PVC follows (RWO volume re-attaches to the new node). Use Recreate so two Pods never race for the storage.
Hard power loss mid-commitThe newest un-fsynced SQLite commit may be lost. Worst case: one step reruns (replay-safe tools) or is reported interrupted to the model. Acceptable for most agent work; use a Postgres-backed storage backend if you need stronger guarantees.
Image update / rolling deployRecreate stops the old Pod, starts the new one, which resumes unfinished work. Registry code updates are picked up automatically (conversations store extension names, not code).

6.3 Scaling patterns

  • Many agents (recommended): N Deployments, each with its own PVC + Service → N independent durable agents. This is the intended pattern and gives clean isolation.
  • HA failover for one agent: with built-in SQLite, failover = a new Pod attaching to the same PVC (Recreate handles it). With a Postgres-backed custom storage backend (small interface + conformance suite), any Pod can take over — true multi-replica HA.
  • Per-conversation isolation: the env function builds an execution environment per conversation from its cwd, so different conversations can point at different directories or containers without touching the harness. A custom env can even set one id per container so equal ids see the same files.
  • Many humans, one agent: clients attach to the same Pod's API; forks give threads their own conversations; ownership kinds decide what aborts reach.

7.2 Recommended external contract (HTTP + SSE)

The pattern Vercel's durable-harness documents, translated to k8s:

EndpointPurpose
POST /tasks{ conversationId?, content, requestId } → durably admits the task; returns submission id + status. Client-chosen requestId (e.g., a CI run id) makes retries safe — same id + same content = same submission, never a duplicate run.
GET /stream?conversationId=…&cursor=…SSE from watchEvents(). No cursor → full current view + live stream. With cursor (last event id) → continues with nothing lost or repeated. 204 when idle.
POST /steer{ conversationId, content } → submit({ whenBusy: "steer" }); reaches the model at its next model call.
POST /forkCreate a thread from an entry; returns the new conversation id for further tasks.
GET /usage?conversationId=…Read the pi.usage document (tokens/cost).

The requestId pattern is the key contract. An external system — CI job, webhook, Slack bot, another agent — can safely retry any submission. This is what makes "give it tasks from the outside" robust: at-least-once delivery over HTTP becomes exactly-once execution in the harness.

7.4 Multi-user steering

  • Any client can attach to any conversation and steer it; a steer from another request takes the session over (the previous request's stream follows along).
  • Forks model threads: each thread is its own conversation with its own agent config — e.g., a cheap read-only reviewer in one thread, the full coding agent in another.
  • Ownership kinds (ownerless, task-owned, conversation-owned) decide what an abort reaches — useful for access control and cleanup semantics.

9.6 Honest gaps (what you'd have to build)

  1. The tools themselves. Browser, vector memory, TTS/STT, image generation: Pi Durable gives the mechanism, not the implementations. Hermes's 70+ tools are years of accumulation; you start from read/write/edit/bash + codemode and add what you need.
  2. Platform adapters. Slack/Telegram/Discord/etc. webhooks are application code — each is small (webhook → submit, stream → post).
  3. Vector search. Run a DB service, expose via tool.
  4. Language ecosystem. Both competitors' plugin ecosystems are Python; Pi Durable extensions are TypeScript.

9.7 What Pi Durable adds that neither has

  • Step-level durable execution: crash mid-tool-call → any new process resumes from the last checkpoint; interrupted unsafe tools reported to the model, safe ones rerun.
  • Exactly-once submissions (requestId) — webhook/CI retries can't double-run work.
  • Infinitely long conversations with background compaction and searchable history.
  • Atomic app state (documents committed with the transcript).
  • Malleable registry — hot-swap tools/prompts on a live agent without restart.
  • Multiplayer steering of running conversations from any number of clients.

Bottom line: every Hermes / Agent Zero feature maps onto Pi Durable primitives, mostly 1:1 (tools, skills, memory-as-documents, cron-as-background-tasks, subagents, code mode, hooks, per-conversation sandboxes). The effort is in the glue — tool implementations, platform adapters, a vector backend, and a UI. And the result would be more robust than either competitor, because both lack the durable-execution layer that is Pi Durable's entire reason to exist. Rough effort split for "Hermes or Agent Zero on Pi Durable": ~30% core harness wiring (days), ~50% tools + adapters (weeks), ~20% UI polish — with durability coming for free underneath all of it.

10Risks & open questions

Experimental API. The package is explicitly experimental and the API changes without notice. Pin exact versions and expect to track releases actively.

  • Single-owner storage. No built-in multi-process locking or HA. Plan around it: one Pod per agent, or implement a Postgres-backed storage backend (small interface, conformance suite included) for true multi-replica failover.
  • Commit durability window. With SQLite, the newest commits may be lost on power/host failure (per Temporal's write-up). Worst case is one step rerunning or being reported interrupted — usually fine, but know it.
  • Execution environment security. NodeExecutionEnv gives tools real filesystem/shell access to the Pod. Isolate per conversation via cwd / custom env ids, or run tools in nested containers/sandboxes (see Vercel's sandbox pattern for the threat model). Non-replay-safe external effects can never be undone — that's on your tool design.
  • Cost controls. Usage is tracked per conversation; hooks (beforeTool) + budgets are how you gate expensive or dangerous actions. Wire approval flows through memos so they survive restarts.
  • TypeScript only (for now). Earendil says ports to other languages aren't ruled out, but the focus is TS — any JS runtime works for hosting.
